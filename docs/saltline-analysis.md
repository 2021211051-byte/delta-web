# Saltline 技术分析与高质量网页 FPS 制作指南

## 1. 文档目的

本文用于分析 Saltline 的模型、手部、动画、材质、渲染和工程组织，并总结这些质量是如何形成的。

目标读者是后续参与游戏开发的 AI 或开发者。重点不是复制某一段源码，而是复用它的制作方法和验收标准。

## 2. 参考项目与来源

- 项目：Saltline
- 类型：浏览器第一人称射击游戏
- 原始实验由 Claude Fable 5.2 生成，实验运行者为 Felix Rieseberg。
- 公开镜像：https://github.com/realcodebear/saltline-fable-5.2
- 原始 Artifact：https://claude.ai/artifact/BGY1SztrAYcJQHSsnHHGmp
- 本项目中的许可记录：`licenses/Saltline-MIT.txt`

原始项目把 Three.js、游戏逻辑、模型生成、纹理生成和声音生成集中在单 HTML 中。本项目为便于维护，已将脚本拆出并格式化。当前分析对应文件为 `public/js/saltline-core.js`。

## 3. 最重要的结论

Saltline 的质量不是来自单纯增加多边形，也不是因为打开了“光线追踪”。

它的优势来自多个系统同时成立：

1. 模型轮廓和比例正确。
2. 手部围绕真实握持关系建模。
3. 材质区分金属、聚合物、皮革和织物。
4. 动画保持手、弹匣、枪机和枪身之间的正确关系。
5. 光照、阴影、反射和后期处理共同展示模型细节。
6. 音效、后坐力、移动和界面反馈与动作同步。
7. 有独立的视觉展示和检查入口。

## 4. 渲染与“光线追踪”的真实情况

### 4.1 它不是硬件光线追踪

项目使用 WebGL 光栅化渲染。没有使用硬件 RT Core、路径追踪或逐像素全局光线求交。

所谓“光追感”，主要来自以下技术的组合。

### 4.2 方向光与软阴影

相关位置：

- 渲染器与太阳光：`public/js/saltline-core.js:36904`
- 自定义软阴影：`public/js/saltline-core.js:35798`

实现要点：

- 使用方向光模拟太阳。
- 使用阴影贴图记录遮挡关系。
- 自定义阴影着色器先搜索遮挡物，再根据遮挡距离决定半影范围。
- 接近 PCSS（Percentage-Closer Soft Shadows）的思路，不是光线追踪。
- 使用接收面深度梯度降低阴影偏移造成的接触错误。

### 4.3 屏幕空间环境遮蔽

渲染器根据深度信息加强接触区域和凹陷处的暗部。

作用：

- 让物体与地面接触更明确。
- 增强墙角、机械缝隙和装备层次。
- 减少模型的“漂浮感”和白模感。

### 4.4 平面反射

相关位置：`public/js/saltline-core.js:54813`

实现方式：

1. 将摄像机镜像到反射面的另一侧。
2. 用镜像摄像机把场景渲染到纹理。
3. 将纹理重新投影到地面。

这是额外的一次场景渲染，不是光线追踪。它能提供直观的地面反射，但需要控制分辨率与性能开销。

### 4.5 环境反射与 PBR

天空、环境贴图、金属度、粗糙度和法线共同决定表面反射。

关键原则：

- 金属不能只有灰色，必须有边缘高光和粗糙度差异。
- 皮革、织物和聚合物不能使用与金属相同的高光响应。
- 瞄具玻璃需要透明、反射和分划之间的平衡。
- 材质应服务于模型结构，而不是用深色把细节全部覆盖。

### 4.6 后期处理

项目组合使用了：

- 体积雾与远景空气感。
- 自动曝光。
- 泛光与高光扩散。
- 运动模糊。
- 色调映射。
- 暗角、颗粒和锐化。

典型渲染顺序：

```text
模型与灯光
→ 阴影贴图
→ 场景颜色与深度
→ AO / 雾 / 反射
→ 曝光、泛光、色调映射
→ 最终画面
```

## 5. 枪械建模为什么精致

相关位置：`public/js/saltline-core.js:64426`

### 5.1 先轮廓，后细节

枪械不是从随机零件开始，而是先确定：

- 枪管与消音器的长度。
- 机匣比例。
- 护木形状与散热孔。
- 弹匣宽度与角度。
- 握把倾斜。
- 枪托轮廓。
- 导轨和瞄具高度。

轮廓不正确时，增加更多零件也不会提升真实感。

### 5.2 使用真实的几何分件

代码通过轮廓拉伸、圆柱、曲线、孔洞和重复结构生成：

- 上下机匣。
- 护木与导轨。
- 弹匣与子弹。
- 枪机与拉机柄。
- 瞄具与镜片。
- 握把、枪托、销钉和标识。

### 5.3 网格合并与性能

实测武器约 5.3 万三角形，但只有约 13 个网格。

关键不是面数越高越好，而是：

- 三角形用于有效轮廓和曲面。
- 相同材质的零件合并。
- 控制绘制调用和材质切换。
- 枪口火焰等对象只在需要时显示。

### 5.4 细节必须能被光照看见

倒角、边缘、凹槽和磨损需要配合光照与材质。只把零件做小，但没有法线、粗糙度和高光差异，最终仍会像白模。

## 6. 手部建模与绑定

相关位置：`public/js/saltline-core.js:66034`

手部不是简单的球体或圆柱拼接，而是参数化生成多个区域：

- 手掌曲面。
- 手背护具。
- 缝线和掌根护垫。
- 四根独立手指。
- 拇指与虎口连接面。
- 前臂与袖口。

食指还提供多套姿态，通过顶点插值实现扣扳机动作。

### 手部建模的硬性要求

1. 手掌必须贴合握把或护木。
2. 手指方向必须围绕真实接触面设计。
3. 拇指和虎口不能断开。
4. 前臂必须连接手腕，且坐标不能重复继承。
5. 左右手应使用不同握持点，而不是只做镜像。
6. 换弹时手、弹匣和枪械必须同步运动。
7. 不允许用关闭深度测试来掩盖手与枪的遮挡错误。

## 7. 换弹、拉栓与动作融合

相关位置：`public/js/saltline-core.js:66778`

### 7.1 换弹是一条时间轨迹

换弹不是简单地把枪倾斜，而是分阶段完成：

- 枪体转入便于操作的位置。
- 手离开原握持点。
- 旧弹匣退出。
- 手移动并取新弹匣。
- 新弹匣插入。
- 必要时操作拉机柄或枪机。
- 手回到握持点，枪体复位。

手部位置使用插值，方向使用四元数插值，避免运动中的突然翻转。

### 7.2 战术换弹与空仓换弹应区分

有余弹时不应机械重复所有拉机柄动作；空仓时才加入完整上膛步骤。动作时长、音效与弹药更新也应与阶段对应。

### 7.3 动画需要融合而非互相覆盖

枪身最终姿态由多个因素共同组成：

- 腰射与开镜。
- 行走与冲刺。
- 换弹与检视。
- 后坐力。
- 跳跃与落地。
- 视角移动惯性。
- 呼吸与静止微动。

弹簧动画应带阻尼，且控制不同状态的权重。开镜时应显著降低跳跃和落地摆动，保持瞄准视野稳定。

## 8. 材质、声音与反馈

材质生成入口：`public/js/saltline-core.js:39767`

纹理不只包含颜色，还包括：

- 法线与微表面凹凸。
- 粗糙度变化。
- 污渍与磨损。
- 金属与涂层的区域差异。
- 环境遮蔽信息。

声音需要对应动作事件，例如：

- 弹匣退出。
- 新弹匣插入。
- 枪机复位。
- 空仓与正常射击。
- 脚步、冲刺、爆炸与技能。

声音不应只是与动画无关的单个音频文件。

## 9. 工程结构与视觉检查

项目虽然最初是单文件，但内部仍按功能模块组织：

- 渲染器。
- 材质。
- 地图与碰撞。
- 玩家与输入。
- 武器。
- 敌人。
- 特效与音频。
- HUD 与菜单。

特别重要的是它有独立的武器展示模式，可检查：

- 腰射。
- 开镜。
- 冲刺。
- 开火。
- 换弹与空仓换弹。
- 枪械侧面。
- 手部特写。
- 枪口与瞄具。

这种入口能显著降低视觉问题的定位成本。

## 10. 本次实际开发中暴露的问题

在参考、仿制和融合过程中，出现过的典型错误包括：

- 把圆角方块和更多面数误认为精致模型。
- 手部只是“存在于模型中”，却没有正确露出和握持。
- Blender、GLB、第一人称与第三人称的坐标方向不一致。
- 父子节点重复继承位置，导致手臂或零件偏移。
- 瞄镜封底、镜座或前准星挡住视野。
- 用隐藏或关闭深度测试处理遮挡，而没有修正真正的位置关系。
- 人物蹲伏时压扁模型或脚底穿入地面。
- 联机服务器与客户端的出生点、重力和地图规则不一致。
- 只做语法检查，没有先检查最终画面。
- 在单个长测试中堆积过多流程，使性能问题与产品问题混杂。

这些问题的共同根因是缺少统一的模型规范、坐标约定和视觉验收流程。

## 11. 下次制作同类项目的推荐流程

### 阶段 A：确定参考与验收标准

先明确以下画面：

- 腰射。
- 开镜。
- 换弹。
- 空仓换弹。
- 拉栓。
- 冲刺。
- 跳跃与开镜跳跃。
- 贴墙。
- 人物站立、行走、蹲伏和卧倒。

没有这些验收画面，就不要先扩展地图和技能数量。

### 阶段 B：制作一个完整武器样板

选择一把武器，完成：

- 枪身轮廓。
- 材质与纹理。
- 双手握持。
- 射击与后坐力。
- 开镜。
- 换弹。
- 空仓动作。
- 声音。
- 冲刺与跳跃。
- 贴墙处理。

只有这个完整样板通过后，才制作第二把武器。

### 阶段 C：建立统一规范

统一：

- 米制单位。
- 前后方向。
- 父子坐标。
- 动画基准位置。
- 手部接触点。
- 弹匣与枪机节点名称。
- 服务器与客户端物理参数。

### 阶段 D：建立视觉与性能测试矩阵

必须检查：

- 不同分辨率。
- 高画质与低画质。
- 开镜和腰射。
- 动画开始、中间和结束。
- 墙面与掩体附近。
- 跳跃和落地。
- 低帧率。
- 单人与联机。
- 人物关节和脚底接地。

同时记录：

- 三角形数量。
- 网格与材质数量。
- 绘制调用。
- 阴影与反射开销。
- 实际帧率。

### 阶段 E：最后扩展玩法

在画面和基础操作稳定后，再增加：

- 技能。
- 投掷物。
- 联机同步。
- 地图模式。
- 大厅与设置。
- 更多干员。

## 13. 最终原则

真正值得复用的是 Saltline 的制作方法，而不是单纯复制资产：

> 清晰的真实结构、正确的握持关系、连续的动画、统一的材质渲染，以及针对最终画面的反复验收。

面数、Blender、Three.js 或某个渲染算法都只是工具。作品质量取决于这些工具是否在正确的制作顺序中被使用，以及是否真正检查过玩家最终看到的画面。

## 14. Saltline 的代码结构为什么更稳定

前面的分析主要解释了模型和渲染。进一步阅读启动、事件和主循环后，可以看到 Saltline 的优势还在于工程结构，而不只是美术资源。

### 14.1 统一的上下文对象

启动入口 `public/js/saltline-core.js:72662` 会建立一个共享上下文，集中保存：

- Three.js 与场景。
- 渲染器、相机和物理系统。
- 材质与模型资源。
- 输入、音频、HUD 和玩家。
- 武器、地图、任务和事件系统。
- 画质参数、时间、随机数与调试状态。

各模块接收同一个上下文，而不是通过大量全局变量互相寻找依赖。这使模块间的数据流更清楚。

我们早期项目则同时存在程序模型、Blender 资产、独立第一人称模型、远程人物和多套动画状态，部分逻辑还分别保存在 `game.js`、`models.js`、`delta-multiplayer.js` 和服务器中。职责交叉增加了状态不一致的风险。

### 14.2 模块工厂与可替换实现

Saltline 使用模块工厂生成地图、武器、敌人、材质和特效。每个工厂关注一个明确领域，并返回自己的数据结构与 `update` 方法。

这使得替换实现很自然，例如：

- 正常地图。
- 独立武器展示。
- 敌人展示。
- 特效展示。
- 无实现的调试桩。

我们当前联机层 `delta-multiplayer.js` 同时负责网络、远端人物、投掷物、技能、开镜、冷却、AWM 变体和帧率。虽然功能完整，但职责过多，后续维护应该继续拆分为：

- `weapon-runtime`：武器与手部动画。
- `skill-runtime`：技能、投掷物和冷却。
- `network-runtime`：房间、快照和远端玩家。
- `hud-runtime`：冷却、黄条、帧率与设置。
- `operator-runtime`：人物与关节动画。

### 14.3 启动阶段允许降级，而不是直接崩溃

启动加载器会尝试初始化模块，并在适当位置使用 `dr` 中的桩实现。

这带来两个好处：

1. 调试某一个模块时，不必启动全部游戏。
2. 模块职责需要显式定义，缺少实现时也能运行。

错误处理也较集中：启动失败记录为 fatal，循环中的异常按模块只报告一次，避免刷屏。

我们早期的问题是部分错误被 `try...catch` 静默吞掉，导致“弹药减少但没有服务器命中”或“模型看似加载成功”的假正常状态。后续应坚持：允许降级，但错误必须可见、可定位。

### 14.4 事件总线解耦功能

`public/js/saltline-core.js:35012` 定义了一个轻量事件系统：

- `on` 注册事件。
- `off` 注销事件。
- `emit` 分发事件并隔离监听器异常。

换弹阶段、射击、命中、警报和任务状态通过事件传递，避免所有模块直接调用彼此。

我们的部分实现则同时存在：

- WebSocket 回调。
- DOM 事件监听。
- Saltline 事件总线。
- 每帧直接状态赋值。

这些渠道如果没有统一事件名称和生命周期，就容易出现重复监听、旧状态覆盖和重复触发。后续应统一为：

- 本地游戏事件负责表现。
- 网络事件负责同步。
- 每帧只处理插值和展示，不重复决定业务状态。
- 模块销毁时移除全部监听。

### 14.5 主循环顺序明确

`public/js/saltline-core.js:72849` 的主循环明确区分：

1. 输入。
2. 游戏状态。
3. 玩家。
4. 武器。
5. 敌人。
6. 特效与地面。
7. 音频与 HUD。
8. 渲染。

展示模式与正常游戏更新分开，帧间隔有上限，防止切换标签页后物理跳变。单个模块出错不会破坏整个循环。

我们的自定义 `delta` 更新插入在武器之后，导致部分开镜状态、手部动画和网络状态必须在同一帧内协调。后续应明确：

- 输入与业务规则。
- 本地物理。
- 网络快照。
- 动画与模型。
- HUD。
- 最终渲染。

### 14.6 物理接口复用

`public/js/saltline-core.js:40158` 集中处理碰撞体、射线和地面高度。玩家、武器、敌人、导航和投掷物都使用同一物理接口。

我们一度同时存在：

- Saltline 物理碰撞。
- `shared/physics.js` 的 AABB 碰撞。
- 服务器端命中检测。
- 前端武器贴墙处理。

这些实现虽然目的不同，但如果地图定义不统一，就会产生“本地无法穿墙，但服务器认为穿过”或“预览与实际落点不同”的问题。后续应让地图定义只产生一份碰撞数据，再由客户端物理与服务器命中共同消费。

## 15. 为什么 Saltline 的模型与代码结构互相促进

Saltline 的模型工厂直接输出节点和动画接口，因此模型从创建之初就考虑：

- 哪些节点控制枪机。
- 哪些节点控制弹匣。
- 左右手分别在哪里。
- 动画如何访问这些节点。
- 材质如何分组与合并。

这比“先导出模型，再猜测各节点怎么动”更稳定。

我们后来使用 Blender 后虽然改善了几何质量，但仍出现过动画基准错误、手部遮挡和父子变换重复继承。说明模型文件本身不能替代接口设计。

后续制作资产时应同时交付：

- 模型文件。
- 节点命名规范。
- 坐标与尺度规范。
- 动画剪辑。
- 握持点。
- 材质分组。
- 可视化检查页。

## 16. 与我们项目的对比：不能简单说谁全面更好

Saltline 的强项是：

- 统一的渲染与动画管线。
- 完整的单武器细节。
- 本地游戏状态和模块边界。
- 直接生成模型和纹理，减少资产转换。
- 独立的视觉调试入口。

我们项目的优势是：

- 真实房间制联机。
- 多干员与技能。
- 独立靶场和原港口地图。
- Blender 资产管线。
- 更完整的设置与中文界面。

但 Saltline 的这些“好”不能直接替代工程验证。我们还需要解决：

- 自定义层职责过多。
- 多套状态并存。
- 监听器生命周期不清。
- 动画与网络状态不同步。
- 先扩展功能、后补视觉检查的问题。

因此正确做法不是继续堆功能，而是保持现有联机优势，同时吸收 Saltline 的结构化实现方式。

## 17. 推荐的后续项目架构

建议逐步形成以下结构：

```text
AppContext
├─ renderer / scene / camera
├─ assets
├─ physics
├─ input
├─ weapon-runtime
├─ skill-runtime
├─ operator-runtime
├─ network-runtime
├─ hud-runtime
├─ audio-runtime
└─ events
```

每个模块都应具有：

- `init()`：明确创建资源。
- `update(dt)`：只处理本模块应更新的状态。
- `dispose()`：释放模型、纹理、监听器和音频。
- `debug()`：提供独立展示或状态快照。

尤其需要坚持：

- 不用大量隐式全局状态。
- 不用静默 `catch` 掩盖错误。
- 不在每帧重复决定一次性的业务事件。
- 不让展示层直接修改服务器状态。
- 不在多个模块中分别实现同一套动画或物理规则。

## 18. 最终补充

Saltline 真正领先的地方，是它从创建对象开始就明确了模块边界、数据流和调试方式。

我后续项目也应该做到：

> 模型与动画有统一接口，业务与展示分离，物理与服务器共享规则，所有关键状态都能被独立验证。

这比继续增加模型面数或零散修补更能长期提升作品质量。
